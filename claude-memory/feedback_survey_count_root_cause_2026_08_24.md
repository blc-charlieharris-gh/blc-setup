Session on 2026-08-24 traced a "still shows 5" complaint (Arktek surveys) through FOUR separate surfaces that each independently counted surveys wrong, in different directions (over- and under-count): `usePeriodBookings.js` (Performance headline), SQL fn `ad_windowed_totals` (Reports + per-ad table), SQL fn `list_bookings_for_ad` (ad drilldown list), `useCostOfSupply.js`. All four needed the same fix, see [[reference_placed_with_company_id_survey_truth]].

**Why: check every surface, not just the one the user is looking at.** A number being "right" on Performance doesn't mean Reports/Cost of Supply/a drilldown agree, they can each have their own independent query with the same root bug or a different one. Grep for every consumer of the underlying table/RPC before declaring a fix complete.

**How to apply the fix when MCP is read-only and no Supabase CLI is installed (this session's environment):**
- SQL function changes: give the user the full `CREATE OR REPLACE FUNCTION ...` statement to paste into the Supabase dashboard SQL editor (Project → SQL Editor → New query) and run directly. Verify the logic first via equivalent read-only `SELECT`/CTE queries (execute_sql works fine for SELECT) before handing it over, since you can't test the actual function live yourself.
- Edge function changes: same pattern, works via the dashboard's Edge Functions → [function] → inline code editor → paste + deploy. No CLI needed. If the function imports shared `_shared/*.ts` helpers, the dashboard editor is typically single-file, so give a **self-contained inlined copy** (fold the shared imports directly into the pasted file) rather than the repo's multi-file version. Remind them to turn OFF "Enforce JWT verification" if the function needs to stay public.
- After the user applies either, verify it actually took effect: for SQL, re-`SELECT` the changed object/data; for an edge function, check `mcp__supabase__list_edge_functions` for `status: ACTIVE` and `curl` the live URL directly with a real or garbage payload. Don't just trust "I ran it" or "done" — this session (2026-08-25) a user reported "Failed to fetch" from the browser after deploying; direct `curl` against the function (including a CORS preflight OPTIONS request) proved the backend was fine, the issue was deploy-propagation timing on the frontend side. Test both ends before concluding which one's actually broken.
- A migration file merged into git does NOT apply itself, there was no migration-apply CI in this repo. Always say this explicitly or the user will assume merging = live.
- **Confirmed DDL specifically fails, not just inferred:** `mcp__supabase__execute_sql` on `ALTER TABLE ... ADD COLUMN` returns `ERROR: 25006: cannot execute ALTER TABLE in a read-only transaction` (2026-08-25). Don't retry hoping for a different result.
- `npx supabase <command>` runs fine (no global install needed) but `supabase login` requires a browser OAuth flow this environment can't complete, and no `SUPABASE_ACCESS_TOKEN` is set in `.env`/`.env.local` to skip it. `SUPABASE_SERVICE_ROLE_KEY` (which IS in `.env`) is a PostgREST API key, not usable for CLI auth or DDL.
- Confirmed 2026-09-08 exactly why: this repo's own deploy scripts (`scripts/one-shot-deploy-agent-execute.mjs`, `scripts/deploy-lead-pipeline.mjs`) use the Supabase Management API (`https://api.supabase.com/v1/projects/<ref>/functions/deploy`), auth'd with a personal access token read from `$HOME/AppData/Roaming/supabase/access-token` — a Windows path, Serafim's machine. No equivalent token exists anywhere on the Mac (checked `~/.supabase`, `~/Library/Application Support/supabase`, `~/.config/supabase`, `.env*`). So on this machine there is no Management-API path either, dashboard paste is the ONLY option for both SQL functions and edge functions, not just a fallback. Direct DDL via `mcp__supabase__execute_sql` is also blocked outright by the auto-mode classifier for a prod `CREATE OR REPLACE FUNCTION`, don't bother retrying it. See [[feedback_paste_ready_code_must_be_own_text]] for how to actually hand over the paste content once you've written it.
- `mcp__supabase__query_logs` can fail with a generic "Backend error! Retry your query" on trivially simple queries, unrelated to anything you did — if it happens, that's the logs API being down, fall back to direct `curl` testing instead of assuming your function is broken.

**Git gotcha hit 3 times this session:** `git commit -- <path> -m "message"` fails or misbehaves (everything after `--` is treated as pathspec, swallowing `-m` and the message text). Always put `-m "message"` BEFORE the `--`/pathspec: `git commit -m "message" -- <path>`. Also: `git commit <path>` alone (no `--`) fails for untracked new files with "did not match any files" even though the file exists, must `git add <path>` first, then commit with an explicit pathspec.
